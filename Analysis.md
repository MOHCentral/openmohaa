# OpenMOHAA Scripting Engine Analysis

## 1. Core Architecture Location

The core scripting engine is distributed across three main directories:
*   **`code/script/`**: Contains the Virtual Machine (`ScriptVM`), variable handling (`ScriptVariable`), and the compiler (`ScriptCompiler`).
*   **`code/corepp/`**: Contains the fundamental Event and Listener system (`listener.h`, `listener.cpp`, `class.h`). This is the bridge between C++ and Scripts.
*   **`code/fgame/`**: Contains the game-specific bindings. `ScriptThread` (in `scriptthread.cpp`) is the main interface exposed to the game logic, inheriting from `Listener` and wrapping `ScriptVM`.

## 2. Architectural Map

### Virtual Machine (VM) Process
1.  **Parsing/Compilation**: When a `.scr` file is loaded, `ScriptCompiler` parses the text and compiles it into bytecodes (`code/script/scriptopcodes.h`).
2.  **Execution**: `ScriptVM::Execute` runs a loop processing these opcodes.
3.  **State Management**: `ScriptThread` manages the execution state (Running, Waiting, Suspended) and timing.

### Event & Binding System
The engine uses a powerful introspection-like system via C++ macros.

*   **`Event`**: Represents a command or message. It holds arguments (`ScriptVariable` list) and an event ID.
*   **`Listener`**: The base class for any object that can respond to events.
*   **`CLASS_DECLARATION`**: A macro used to register a C++ class into the scripting system. It creates a `ClassDef` structure containing a lookup table mapping Event IDs (or names) to C++ member functions.

### Execution Flow: `iprintln "Hello"`
1.  **Script**: `iprintln "Hello"` is encountered.
2.  **VM**: The VM identifies `iprintln` as a command.
3.  **Dispatch**: The VM creates an `Event` object with command "iprintln" and argument "Hello".
4.  **Routing**: The event is passed to the current `ScriptThread`'s `ProcessEvent` method.
5.  **Lookup**: `Listener::ProcessEvent` looks up the event in `ScriptThread::Responses` (generated by `CLASS_DECLARATION`).
6.  **Call**: It finds `&EV_ScriptThread_IPrintln` maps to `&ScriptThread::IPrintln`.
7.  **Execution**: `ScriptThread::IPrintln(Event *ev)` is called. It retrieves the string argument and calls `gi.SendServerCommand` to print it.

## 3. Quality & Evaluation

### Legacy Code Smells
*   **Manual Memory Management**: Heavy use of `gi.Malloc` and `gi.Free` alongside `new`/`delete`.
*   **String Handling**: Occasional use of fixed-size buffers (`char buf[1024]`) which can be prone to overflows if not carefully checked (`Q_strncpyz` is often used, which is good, but risk remains).
*   **Global State**: `Director` and `level` globals manage the overall script state, which makes thread-safety (for actual OS threads) difficult.

### Memory Management
*   **Script Objects**: `ScriptVariable` uses a smart-pointer-like approach or deep copies depending on type.
*   **Event Cleanup**: Events are often allocated and must be manually deleted or handled by the `Event_allocator`.
*   **Recursion**: The `ProcessEvent` system can recurse deeply (Event triggers Event), potentially leading to stack overflow in extreme cases.

### Critical Path (Single Command)
`VM Loop` -> `Fetch Opcode` -> `Create Event` -> `Listener::ProcessEvent` -> `ClassDef::GetDef` -> `C++ Method` -> `Return`

### Danger Zones
*   **Blocking Main Thread**: C++ commands must **never** block (e.g., long file I/O or network requests) as they freeze the entire server.
*   **Pointer Validity**: Passing `Entity*` or `Listener*` to async tasks is dangerous as the object might be destroyed before the task completes. Use `SafePtr` or handles (`entnum`).
*   **Infinite Loops**: Scripts calling events that trigger the same script can cause stack overflows/freezes.

# Feature Implementation: YAML & JSON Support

I have implemented the `ScriptYAML` class to support YAML and JSON parsing via `yaml-cpp`.

## Changes Applied
1.  **Build System**:
    *   Created `cmake/libraries/yaml-cpp.cmake` to handle the dependency.
    *   Updated `cmake/libraries/all.cmake` to include the new library.
    *   Updated `cmake/basegame.cmake` to link `yaml-cpp` and include the new source files.
2.  **Source Code**:
    *   `code/fgame/scriptyaml.h`: Header definition.
    *   `code/fgame/scriptyaml.cpp`: Implementation of `load`, `get`, `parse`, `save`, and `serialize`.

## Usage in Script
```c
local.yaml = spawn ScriptYAML
local.success = local.yaml.load "config.yaml"
if (local.success) {
    local.health = local.yaml.get "player.stats.health"
    iprintln ("Health from YAML: " + local.health)
}
```

## Dependencies
You must place the `yaml-cpp` library in `thirdparty/yaml-cpp`. If using git:
```bash
git submodule add https://github.com/jbeder/yaml-cpp.git thirdparty/yaml-cpp
```
